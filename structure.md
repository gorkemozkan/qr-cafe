# Project Structure

Where things live in `qr-cafe` (package name `only-menu`), and the rule that
decides where a new file goes.

## Top level

```
qr-cafe/
├── app/                  Next.js App Router: pages, layouts, API routes
├── components/           React components, grouped by feature then by role
├── lib/                  Framework-free logic: data access, validation, security
├── hooks/                Reusable client-side React hooks
├── context/              React context providers that are not data-layer
├── types/                Generated Supabase database types
├── messages/             next-intl translation catalogues (en, tr)
├── supabase/             config.toml and the ordered SQL migration chain
├── scripts/              Shell helpers for migrations and releases
├── docs/                 Long-form documentation
├── public/               Static assets served as-is
├── middleware.ts         Auth gate + locale cookie, runs before every page
├── i18n.ts               Locale list and next-intl request config
├── config.ts             Storage bucket names
└── next.config.ts        Image hosts and security headers
```

`config.ts`, `i18n.ts` and `middleware.ts` sit at the repository root rather
than under `lib/` because Next.js and `next-intl` resolve them from there.

## Path alias

`tsconfig.json` maps `@/*` to the repository root, so every import is absolute
from the root regardless of nesting depth:

```ts
import { createClient } from "@/lib/supabase/server";
import { cafeSchema } from "@/lib/schema";
```

Relative imports (`../../lib/...`) do not appear in this codebase. Keep it that
way — the alias is what makes files movable.

## `app/` — routing

Route groups separate the three audiences. The parenthesised segments do not
appear in URLs.

```
app/
├── (menu)/[slug]/            Public QR menu — the page a diner scans into
│   ├── page.tsx              Server component, fetches through the repository
│   ├── opengraph-image.tsx   Generated social preview image
│   └── not-found.tsx
├── (admin)/admin/
│   ├── auth/login/           Unauthenticated
│   └── app/                  Authenticated: dashboard, cafes, categories
├── api/                      Route handlers (see below)
├── page.tsx                  Marketing landing page
├── privacy/, terms/, error/  Static pages
└── layout.tsx                Root layout: providers, theme, fonts
```

### `app/api/` — route handlers

One directory per resource, one directory per action. The shape is consistent:

```
api/
├── auth/{login,logout}/
├── cafe/{route.ts, create, update, [id]}/
├── category/{create, update, sort-order, [id], cafe/[id]}/
├── product/{create, update, [id], cafe/[id], category/[id]}/
├── public/cafe/{route.ts, [slug]}/     No authentication; the menu API
├── storage/{upload, delete}/
├── gdpr/{export, delete}/
├── stats/
└── [...slug]/                          Catch-all: rate-limited 404
```

`api/[...slug]/route.ts` answers every unmatched API path with a rate-limited
404 for all seven HTTP methods, so probing for endpoints costs the caller their
rate-limit budget.

Anything under `api/public/` is reachable without a session. Everything else
depends on the Supabase session cookie and on row-level security.

## `components/` — feature directories plus `ui/` and `common/`

```
components/
├── ui/          shadcn/ui primitives (button, dialog, table …) — lowercase files
├── common/      App-wide composites: DataTable, FormSheet, Captcha, ErrorBoundary
├── auth/        LoginForm, UserDropdown
├── cafe/        CafeForm, CafeList, CafeCreateSheet, CafeQRPreviewDialog …
├── category/    CategoryForm, CategoryList, CategoryCreateModal …
├── product/     ProductForm, ProductList, ProductCreateSheet …
├── dashboard/   DashboardStatCards
├── gdpr/        Export and deletion dialogs
├── landing/     Marketing page sections (Hero, Features, CTASection, Footer)
├── menu/        SimpleMenu/ — the public menu renderer
└── providers/   QueryProvider
```

Two naming conventions coexist on purpose:

- `ui/` uses lowercase kebab-case (`dropdown-menu.tsx`) because those files are
  generated by the shadcn CLI and are meant to be regenerated.
- Everything else uses PascalCase matching the exported component.

Within a feature directory the recurring roles are `*Form` (the fields plus
validation), `*List` (the table), `*CreateSheet` / `*EditSheet` / `*Modal` (the
container that opens the form), and `*Dropdown` (row actions).

## `lib/` — logic with no React in it

```
lib/
├── api-client.ts          fetch wrapper; throws Error with a `status` property
├── repositories/          One class per resource, extends BaseRepository
│   ├── base-repository.ts
│   ├── cafe-repository.ts, category-repository.ts, product-repository.ts
│   ├── auth-repository.ts, gdpr-repository.ts, storage-repository.ts
│   └── public-menu-repository.ts
├── supabase/
│   ├── client.ts          Browser client
│   ├── server.ts          Server client, reads the cookie store
│   ├── middleware.ts      Session refresh + redirect rules
│   └── storage.ts         Bucket upload/delete helpers
├── services/
│   └── sortingService.ts  Drag-and-drop reordering
├── schema.ts              All zod schemas and their inferred types
├── security.ts            CSRF origin check, CSP builder, file/XSS validation
├── payload-validation.ts  Per-content-type request size limits
├── rate-limiter-redis.ts  Four Upstash sliding-window limiters
├── redis.ts               Upstash client and cache key helpers
├── http.ts                Status/message constants, createSafeErrorResponse
├── env.ts                 Environment resolution — throws on missing config
├── query.ts               React Query key factory
├── format.ts, dom.ts, utils.ts
```

`lib/` never imports from `components/`. The dependency direction is
`app/` → `components/` → `hooks/` → `lib/`, and `app/` may reach into `lib/`
directly.

## `hooks/`

`useCafeData`, `useDataTable`, `useSorting`, `useRequest`, `useResponsive`,
`useCopyToClipboard`. A hook belongs here once a second feature needs it;
until then it stays in the component file that uses it.

## `supabase/`

```
supabase/
├── config.toml       Local stack ports; Postgres major version 17
└── migrations/       Timestamped SQL, applied in filename order
```

Migrations are append-only. The filename is
`<YYYYMMDDHHMMSS>_<description>.sql` and `scripts/create-migration.sh`
generates it from `supabase db diff`.

`types/db.ts` is generated from this schema by
`supabase gen types typescript`. It is checked in, so it drifts if someone
writes a migration by hand without regenerating — treat a mismatch between
`types/db.ts` and `supabase/migrations/` as a bug.

## `messages/`

`en.json` and `tr.json`. The locale list in `i18n.ts` must match the files
present here exactly; a locale without a file makes `getRequestConfig` throw
and returns a 500.

## Where does a new file go?

| You are adding | It goes in |
| --- | --- |
| A page or an API endpoint | `app/` under the matching route group |
| A component used by one feature | `components/<feature>/` |
| A component used by three features | `components/common/` |
| A shadcn primitive | `components/ui/` (via the CLI) |
| Data fetching for a resource | `lib/repositories/` |
| A zod schema | `lib/schema.ts` — one file, not one per resource |
| A database change | a new file in `supabase/migrations/` |
| A translated string | both `messages/en.json` and `messages/tr.json` |

## Not documented here

Tooling configuration — `biome.json`, `postcss.config.mjs`,
`components.json`, `.github/workflows/` — is deliberately left out. See
[architecture.md](./architecture.md) for how the runtime pieces fit together
and `docs/SDD.md` for the full design description.
